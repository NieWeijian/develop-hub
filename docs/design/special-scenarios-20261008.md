## 统一用例库与发布验证

四项特殊场景以真实 TestCase 注册到用例库，执行方式为 `gated`。用例库包含26项自动用例和4项人工门控用例；全量发布清单包含26项自动用例、4项人工门控及2项待定义场景。普通自动批量与定时回归仍只调度自动用例。用例卡片提供门控步骤、操作说明、记录要求和定向启动入口。

发布清单冻结场景定义、执行器与工具摘要。从清单点击“准备执行”先展开模组和操作者表单；点击“烧录候选并开始门控”才创建关联 SpecialRun 及专属候选准备轮次。准备轮次复用固定候选镜像，烧录后执行 BASIC-VERSION。只有镜像、交付、Controller配置、分区写入、启动、CPU与USB身份验证满足要求，才开放人工步骤。准备与门控共享同一个测试台占用，其他任务不能在交接期间插入。

SpecialRun保存计划、清单项、候选指纹、准备轮次和清单定义摘要。清单实时显示准备中、等待操作、执行中、通过、失败或阻塞，完成后自动回填，并保留原始门控记录与参数。独立入口的历史通过结果不能仅凭版本文字引用为发布证据。OTA按损坏包、错误包名、升级中断电分别取最近一次结果，三种全部通过才算该项通过。

旧的开放计划通过有操作者、原因和修订号的“同步特殊场景定义”操作补齐四项定义；保持清单项ID、已有自动测试历史和已冻结报告。尚未执行的四项显示“人工门控 · 未测”，RGB/IMU和多模组同步继续为待定义。

## 执行结构

175 的数据库保存 SpecialRun、冻结定义、产品与测试台、CPU serial/USB 端口/固件版本、工具及执行器摘要、步骤、操作者输入和事件。前端只展示并提交当前门控，不能自行推进权威状态。每次提交携带步骤 ID 和 revision；完全相同的请求返回原动作，不重复执行写入。

一个人工场景从创建到完成持续占用测试台，等待拔插期间也不会被普通轮次或设备扫描抢占。每一步点击确认才执行；刷新后恢复当前状态。服务重启不重放硬件动作，运行中步骤变为中断并保留占用。取消会向本步骤发送停止标记；远端状态未知或人工 OTA/老化尚未结束时，需要记录人工停止确认才能释放。

175 经 SSH 把冻结运行包及请求传到 3588 的 `<bench_root>/special-runs/<run_id>/`。运行器只允许定义好的 operation，不接受任意 shell。使用已冻结工具读写模组，重新核对 CPU/USB 身份，命令前检查 USB 连接代次，避免节点复用后写错模组。自2026-10-09起，新运行只回传完整结果JSON与命令/错误摘要；原始日志、协议追踪和输入文件留在3588，远端核验路径、大小和SHA-256后保存元数据。已冻结旧运行遵循原归档策略，历史已归档文件仍可下载。

日志压力的设备明确写入失败（例如 `file-put chunk failed: write failed`、ENOSPC）直接判失败；后续目录、健康或证据处理异常不会覆盖已确定的失败。完成压力但可读目录未显示回收或未收敛也判失败。缺模组、缺目录、传输超时等无法确定测试结论的条件仍为阻塞。是否满盘、是否rolling失效另记诊断证据，不影响已观测写失败的失败结论。旧记录可根据保存的原始命令结果作有审计的失败判定纠正，保留原文件、冻结定义与修订前结果。

## 四个流程与通过边界

| 场景 | 流程 | 判定与记录 |
|---|---|---|
| SN 断电持久化 | 读取基线 → 输入并写 SN → 立即人工断电 → 检查原 USB 端口确实消失 → 同模组插回 → 回读比对 → 确认收尾 | 保存原 SN、目标 SN、写入完成/掉线观测时间、CPU/端口及重启后 SN。目标保留，不在判定前自动恢复。工具本身的即时读回不替代冷启动验证。掉线时间为系统观测上界，不伪称精确断电时刻。 |
| 日志压力 | 读取基线 → 确认累计目标（默认 24 MiB）→ 每片 60000 字节持续 file-put → 检查回收及健康 | 使用独立 `qa-<run-prefix>-NNNN.log`，不覆盖 lasted.log。记录成功字节、失败命令、目录快照和明确 ENOSPC。要求累计超过 20 MiB、观察到测试文件回收、日志总量收敛到 4 MiB 以内及健康检查。明确设备写失败或完成压力后未回收/收敛判失败；缺少必要目录读取能力才阻塞。累计上传不是实际满盘证明，当前 CLI 无剩余容量接口。禁止用 clean-log 冒充 rolling。 |
| 老化 | 读取基线 → USB 串口探测 → 准备/重置历史结果、核对固件时长 → 开始采集 → 采集就绪后人工给座子上电 → 日志判定 | 3588 串口或人工上传完整原始日志共用判定。默认固件周期 14400 秒，采集等待 15000 秒；Hub 的阈值不会改固件 `/data/aging_time`。必须本轮 start、足够 elapsed_sec、健康遥测、温度不超人工设置阈值和 final result=1 reason=duration_elapsed；旧 skip existing result=1、重启、缺结尾不可通过。完整文件最大64 MiB；原始证据明确标识人工或自动来源。 |
| OTA 异常 | 读取基线 → 选择一种异常及3588源包路径/SHA → 生成独立副本 → 按页面命令人工执行 ADB/tar OTA → 提交升级日志/断电时刻 → 自动身份及健康回检 | 每轮仅一种异常，三种需分别建轮。损坏包翻转一字节但保留原 MD5，应在写分区前被拒绝。错名包保留内容及正确 MD5，必须有明确名称拒绝，不能把校验和错误当名称检查。中断需要3588同一时钟带时区的写分区 start 与断电时间，已成功/失败后才断电不算有效注入。无论注入判定成功失败都会尝试恢复检查。 |

## 现场能力与限制

- FTDI USB 串口已在 Windows 识别为 COM15，序列号 AQ04FZUR。3588 内核支持 FTDI 和 CP210x；本次检查时未启用 CH341。将 USB 端接3588后可重新探测 `/dev/serial/by-id`。接线、电平和波特率需现场核对，程序不会自动选板载 ttyS 作为模组串口。
- 串口模式只有显示“采集已就绪”后才能给老化座上电；准备运行包期间不应上电，以免丢失 start。默认不写串口命令。
- 日志 rolling 源码总量限制4 MiB，只管理 `.log/.gz/.pending`，在启动/轮转时清理；传入任意 userdata 文件不保证触发。未测得真实容量边界不能宣称全盘满异常测试完成。
- 现有 `uvc_host_ota` 是 DFU 分区工具，不等价于 tar OTA 异常包测试。首版 tar 注入由操作者执行，页面给出真实包和触发 `.md5` 的命令、状态采集与回检流程。
- 被检查的 OTA 脚本没有包名格式校验，错名但内容/MD5一致时可能继续升级，此时本用例应失败。ADB 切换不代表 OTA monitor 已启动，操作员需确认它实际运行。
- RGB/IMU 的跨175/3588/Windows WSL流程，以及硬同步多模组工具接入，不计入本次完成范围。
